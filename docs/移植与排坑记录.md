## 一、八个真实问题（按严重度排序）

### 1. `python` 命令是坏的（`exit code 9009`）

```
PS> python -V
                                  # 什么都不打印
PS> echo $LASTEXITCODE

```

- `where.exe python` → `C:\Users\Anfield\AppData\Local\Microsoft\WindowsApps\python.exe`（0 字节占位符）
- 该占位符指向的 `PythonSoftwareFoundation.Python.3.13_qbz5n2kfra8p0` 已被卸载/不可用
- 真正可用的是 `py -3.12` 或 `...\Python312\python.exe`（3.12.5，所有依赖都装在这里）

**所以和 openai.py、torch、transformers 全部无关**，`import` 根本没执行过。

### 2. `venv_minrag` 是个死 venv

`venv_minrag\pyvenv.cfg` 里写着：

```
home = C:\Users\Anfield\AppData\Local\Microsoft\WindowsApps\PythonSoftwareFoundation.Python.3.13_qbz5n2kfra8p0
version = 3.13.5
```

它是由那个已消失的商店版 Python 建的，`Scripts\site-packages` 里只有一个 pip。
激活它再跑脚本 = 立刻失败。**已重建**：旧的重命名为 `venv_minrag_broken`，
新的用 `py -3.12 -m venv --system-site-packages venv_minrag` 创建，能直接继承
Python312 里已经装好的 torch / transformers / openai。

### 3. `gpt_4o_mini_complete` 每次调用都抛 TypeError（致命，但被 retry 掩盖）

MiniRAG 调用 LLM 的方式是（`minirag/minirag.py:300`）：

```python
self.llm_model_func = limit_async_func_call(...)(
    partial(self.llm_model_func, hashing_kv=self.llm_response_cache, **self.llm_model_kwargs)
)
```

也就是说**每次调用都会带 `hashing_kv`**。而原版 `minirag/llm/openai.py` 把它原封不动
塞进 `client.chat.completions.create(**kwargs)`：

```
TypeError: AsyncCompletions.create() got an unexpected keyword argument 'hashing_kv'
```

外面套了 `@retry(stop_after_attempt(3), wait_exponential(min=4,max=10))`，
于是每一次 LLM 请求都会 **先静默重试 3 次、白等 ≈14 秒、再抛出**。
表现为"卡住、很慢、最后报错或空结果"。

### 4. 模型名永远是 `gpt-4o-mini`

原版函数的签名是 `model_name="gpt-4o-mini"`，而 MiniRAG 只会把模型名放进
`global_config["llm_model_name"]`（不会作为参数传进来）。所以哪怕 base_url 对了，
发出去的请求也是 `model="gpt-4o-mini"`，Ollama 只会回 `model not found`。
你在脚本里改 `LLM_MODEL = "phi3.5"` 是**不起作用**的。

### 5. 没有响应缓存 → `insert()` 是 O(n²)

`ainsert()` 在处理完文档后，会把**所有已处理文档的所有 chunk** 再丢给
`extract_entities()`（`minirag/minirag.py:362`）。每个 chunk 要 2~3 次 LLM 调用
（1 次抽取 + 1 次 gleaning + 1 次是否继续）。
原版函数完全没理会 `hashing_kv`，等于**零缓存**：

- 第 1 篇：2 次调用
- 第 5 篇：约 10 次
- 第 100 篇：约 200 次

这就是你 `LiHua-World\minirag.log` 里耗时 23s → 32s → 58s → 45s 逐次变长的原因。

### 6. `OPENAI_API_BASE` 其实是对的（但没被当成唯一出路）

`openai` SDK v1+ 认的是 `OPENAI_BASE_URL`，而 `OPENAI_API_BASE` 只有显式
`base_url=os.environ.get("OPENAI_API_BASE")` 时才生效——MiniRAG 原版恰好是这么写的，
所以**环境变量这条路本身没问题**。踩坑的不是这里。

顺带：`✅ 索引完成` 里的 emoji 在 GBK 控制台下会抛 `UnicodeEncodeError`，
在脚本末尾炸掉最后一行输出。

### 7. phi3.5 不给 system prompt 会跑飞到 1 万 token（实测）

修好前 6 条之后仍然"卡住不动"——因为 phi3.5 3.8B 面对 2218 token 的
`entity_extraction` 指令时会彻底跑偏，实测同一个提示词：

| 配置 | 耗时 | 输出 | 格式对不对 |
| --- | --- | --- | --- |
| `max_tokens=512`，无 system | 12.1s | 412 token 胡言乱语（讲"绯红之门的授勋"） | ✗ |
| `max_tokens=1024`，无 system | 18.8s | 859 token 胡言乱语 | ✗ |
| **不设 max_tokens，无 system** | **277.9s** | **10598 token 散文**，一直到自己写累 | ✗ |
| **加一句 system + `temperature=0.2`** | **5.4s** | `("entity"<|>"Alice"<|>"person"<|>...)` | **✓** |

两件事：

1. **必须给 max_tokens 兜底**。我一开始把原来的 `max_tokens=200` 去掉了（怕截断），
   结果 Ollama 默认 `num_predict=-1`，phi3.5 能自说自话 10 分钟。现在固定 768。
2. **必须给 system prompt**。MiniRAG 调用时从不传 system prompt，所以在
   `gpt_4o_mini_complete` 里补了一句：

   `You are a precise assistant that follows instructions exactly. Answer only what is asked, in exactly the requested format, with no extra commentary...`

   加上之后 phi3.5 变成 5.4 秒、格式正确。**这是把 ETA 从"几小时+一堆垃圾实体"
   变成"35 分钟"的关键。**

   > 顺带说明：这也解释了 `LiHua-World_bak` 里那 17 个节点为什么看着像样又有点怪
   > —— 那就是偶尔听话、偶尔跑飞的结果。已重命名为 `LiHua-World_bak` 留档，
   > 正式索引从头重建。

### 8. 一次 500 就能杀掉整个进程 → `RetryError`

第一次正经跑，跑到第 9 批（72/442 篇）时进程直接没了，`logs\index_err.log` 里是：

```
openai.InternalServerError: Error code: 500 - prediction aborted, token repeat limit reached
tenacity.RetryError: RetryError[<Future ... raised InternalServerError>]
```

phi3.5 偶尔会陷进复读循环，llama.cpp 主动中止并回 500；原来的 `@retry` 重试 3 次
（每次白等 4~10 秒）后把异常继续往上抛，`rag.insert()` 整批失败 → 脚本退出。
**一个分片复读，442 篇全白跑。**

现在 `gpt_4o_mini_complete` 里：遇到 "token repeat limit / prediction aborted"
立刻放弃这个分片并 `return ""`；其它错误重试 3 次仍失败也 `return ""`，
记一条 WARNING，不再让单个分片炸掉整轮。

失败的分片**不进缓存**，所以把同一条命令再跑一遍就会只重试它们（其余全命中缓存，很快）。

### 9. 最重要的坏消息：phi3.5 处理不了长/带 emoji 的 chunk

把索引跑起来之后统计了一下：**68 个 chunk 里只有 28 个真正抽出了实体，40 个是空的。**
拿其中一个失败的 chunk（4082 字符的多人聊天，含大量 emoji）直接做对照实验：

| 模型 | 耗时 | 输出 |
| --- | --- | --- |
| `phi3.5` | 2.9s | 75 字符 `# Instruction: ... ```cpp:` 之类的垃圾 |
| `qwen3:8b`（`think: false`） | 31.6s | `("entity"<|>"LiHua"<|>"person"<|>...)` 完整正确 |

结论很硬：

- **phi3.5 = 快，但长文档/emoji 会直接崩格式**，约 40~60% 的 chunk 抽不出实体，
  索引会稀疏得没法做 QA。
- **qwen3:8b = 慢约 10 倍/次，但格式基本都对**。你本机已经 `ollama pull qwen3:8b` 了。

所以如果你要的是"能用来跑 Step_1 QA 的索引"，建议：

```powershell
# 1) 清掉记录，让之前抽失败的 chunk 重抽
del LiHua-World\kv_store_extracted_chunks.json
# 2) 换 qwen3:8b，并且关掉 gleaning 省一半调用
.\run_index.bat --llm qwen3:8b --gleaning 0
```

代价是 442 篇大约要 3~5 小时（qwen3 每次 30s 上下）。想快就先用 `--limit 100`
跑个能用的子集，或者继续用 phi3.5 接受稀疏索引。

> `think: false` 已经在 `openai.py` 里对 `qwen3 / deepseek-r1 / qwq` 自动开启——
> 不关的话 qwen3 会把 768 token 全花在 ` thinking` 上，返回空字符串。

## 二、改了什么

| 文件 | 改动 |
| --- | --- |
| `minirag/minirag.py` | `ainsert()` 原本每次都把所有已处理 chunk 重新抽实体。加了一个 `extracted_chunks` 记账 KV，抽过的 chunk 不再重抽（`kv_store_extracted_chunks.json`，删掉它就能强制重抽）。这一条把"越跑越慢"变成线性 |
| `minirag/llm/openai.py` | 重写。弹出 `hashing_kv` / `keyword_extraction` / `mode` 等框架内部参数；模型名从 `hashing_kv.global_config["llm_model_name"]` 取；补默认 system prompt、`max_tokens=768`、`temperature=0.2`；按 (base_url, api_key) 复用 `AsyncOpenAI` 客户端；**加 llm_response_cache 读写**；**单个分片 500 / 复读只跳过不炸进程** |
| `reproduce/Step_0_index.py` | 重写。UTF-8 控制台、离线 HF、Ollama 预检、分批 `insert()`、进度/ETA、`--limit` 冒烟测试、`--batch` / `--max-async` / `--gleaning` |
| `reproduce/Step_1_QA.py` | 重写。改用 Ollama + 同一个 embedding；`--limit`、`--mode`、断点续跑、每题耗时 |
| `run_index.bat` / `run_qa.bat` | 双击即用；自动选 venv 或 `py -3.12`，`chcp 65001` + `-u`，结束后 `pause` 不闪退 |
| `venv_minrag` | 重建（`--system-site-packages`） |

**embedding 故意保持 `all-MiniLM-L6-v2` / 384 维不变**：它已经在本地
`~/.cache/huggingface` 里，离线可用；而且和 `LiHua-World\` 里已有的 384 维索引兼容，
不用重头再来。（`bge-m3` 是 1024 维，换它必须清空工作目录重建索引。）

## 五、注意

- `--max-async 4` 是给单卡 Ollama 的安全值。Ollama 新版默认 `OLLAMA_NUM_PARALLEL=1`，
  并发调到 8 也不一定更快（实测瓶颈在单卡生成速度，约 35 tok/s），但更容易 OOM。
- 想更快：`--gleaning 0` 把每块 2 次调用减成 1 次（442 篇从 ~90 分钟降到 ~45 分钟），
  召回略降；`--batch 16` 也能省一点。
- 别删 `kv_store_llm_response_cache.json` 和 `kv_store_extracted_chunks.json`：
  前者让重复 prompt 秒回，后者让已抽过的 chunk 不再重抽。
- phi3.5 只有 3.8B，抽取格式（`<|>` 分隔的元组）偶尔写错、偶尔复读，
  日志里 `entities(duplicated)` 忽多忽少、偶发一条 WARNING 都是正常的，不是 bug。
- 索引可以随时中断：`Ctrl+C` 或直接关窗口，重跑 `run_index.bat` 会接着做
  （已处理的文档跳过，已抽过的 chunk 跳过，已缓存的分片不再调模型）。
