## 1. 实验目的

1. 理解 MiniRAG 与普通 RAG 的差别：它把知识存成**实体—关系图**，检索时走图上的路径，而不是只做向量相似度。
2. 掌握"用本地小模型替代 GPT-4o-mini"时，哪些环节会坏、为什么坏、怎么定位。
3. 得到一份可复现的基线数字：在 8 GB 显存的单卡上，MiniRAG 能做到什么程度。

---

## 2. 实验原理（够用就行）

### 2.1 MiniRAG 做了什么

普通 RAG：文档切块 → 向量化 → 按相似度取 top-k → 塞给大模型。

MiniRAG：文档切块后，**先用大模型从每块里抽出实体和关系**，建成一张图（`graph_chunk_entity_relation.graphml`），
同时把实体名、实体描述、关系、原文块分别向量化。查询时：

1. 让大模型从问题里抽出「答案类型关键词」和「问题里的实体」；
2. 拿这些实体去图上找 2 跳内的邻居，拼出一条推理路径；
3. 沿路径找回原始文本块；
4. 把「实体表 + 原文块」一起塞给大模型作答。

**这就是为什么建索引那么慢**——每块文本都要调 2 次大模型（抽取 + 追问），而 GPT-4o-mini 换成本地 8B 模型后，单次调用从 1 秒变成 15~20 秒。

### 2.2 三种查询模式

| 模式 | 做法 | 本实验结果 |
| --- | --- | --- |
| `mini` | 走图路径（论文主推） | 可用，答案有依据 |
| `light` | 混合检索 | 本机报错，不推荐 |
| `naive` | 纯向量检索原文块 | 可用，作为下限对照 |

### 2.3 索引目录里到底存了什么

`LiHua-World\` 里 10 个文件，缺一不可：

| 文件 | 作用 | 删了会怎样 |
| --- | --- | --- |
| `graph_chunk_entity_relation.graphml` | 实体关系图 | 图没了，mini 模式失效 |
| `vdb_entities.json` | 实体描述向量 | 找不到相关实体 |
| `vdb_entities_name.json` | 实体名向量 | 问题里的实体匹配不上 |
| `vdb_relationships.json` | 关系向量 | 推理路径断掉 |
| `vdb_chunks.json` | 原文块向量 | 找不回原文 |
| `kv_store_text_chunks.json` | 原文块正文 | 同上 |
| `kv_store_doc_status.json` | 每篇文档的处理状态（断点续跑靠它） | 会从头重跑 |
| `kv_store_llm_response_cache.json` | 大模型响应缓存 | 重跑变慢数倍 |
| `kv_store_extracted_chunks.json` | 哪些块已经抽过实体 | 会重复抽取 |
| `kv_store_full_docs.json` | 完整文档 | 影响摘要类查询 |

> ⚠️ 删任何一个都等于破坏索引。要重建就整个目录删掉重来。

## 4. 三个必踩的坑（先看，能省两小时）

| 现象 | 真正原因 | 处置 |
| --- | --- | --- |
| 敲完 `python xxx.py` 回车，**瞬间回到提示符、没有任何输出** | `python` 命令指向了已卸载的商店版占位符（`exit code 9009`），根本没执行 | **永远用 `.bat` 或 `.\venv_minrag\Scripts\python.exe`**，不要用裸 `python` |
| `venv_minrag` 激活后什么都跑不了 | 它是由已消失的 Store Python 3.13 建的 | 已重建；坏了就 `py -3.12 -m venv --system-site-packages venv_minrag` |
| 模型总是答「文中没有提到」 | 上下文被 Ollama 截断（默认窗口 4096 token），或 qwen3 把 token 全花在思考上 | 见第 8 章故障排查 |

> 另外记住一条：**qwen3 的思考模式必须用 Ollama 原生接口的 `think:false` 才能真正关掉**，
> `/v1` 接口上的 `think`、`/no_think`、`chat_template_kwargs` 全部无效。这一条已经写进代码，不用你管，但换模型时要知道。

## 5. 实验步骤

### 第 1 步：建索引（约 1 小时）

**在哪里做：** `E:\miniRAG\MiniRAG`

**做什么：**

```powershell
cd E:\miniRAG\MiniRAG
.\run_index.bat --llm qwen3:8b --gleaning 0
```

参数含义：

| 参数 | 作用 | 建议值 |
| --- | --- | --- |
| `--llm` | 抽取实体用的 Ollama 模型 | `qwen3:8b`（phi3.5 会大面积抽取失败） |
| `--gleaning` | 每块追问几轮 | `0` 速度快一倍；`1` 是论文默认，召回略高 |
| `--batch` | 一次塞几篇文档 | 默认 8，显存紧张就降到 4 |
| `--limit N` | 只处理前 N 篇（试跑用） | 调试时用 5 |

**第一次建议先试跑 5 篇**（约 3 分钟），确认链路通了再跑全量：

```powershell
.\run_index.bat --llm qwen3:8b --gleaning 0 --limit 5 --workingdir .\_test
```

**你应该看到的输出（真实记录）：**


**过程中会经历什么（正常现象，别慌）：**

- 每个 chunk 15~20 秒，进度条 `⠙ Processed N chunks` 会以几十秒一步的速度跳动；
- 每 64 个 chunk 打一行 `checkpoint: 64/266 chunks`，**这是存盘点**，中断了从这里续；
- 偶尔一条 `WARNING: N chunks produced no entities`，属于正常损耗（短文档本来就没实体）；
- 每批耗时 2~3 分钟是正常的，GPU 占用会长期 90%+。

**怎么判断成功了：**

```powershell
.\check_status.bat
```

要看到：

```
已抽到实体  : 466 / 490  [############################..] 95%
知识图谱    : 793 个实体, 933 条关系
判定        : 跑完了 -> [4/4] done: 442 documents in 56.8 min
```

**验收线**：`已抽到实体 ≥ 90%`、`知识图谱 ≥ 700 实体`。低于这个数就按第 8 章排查。

**中断了怎么办：** 直接重跑同一条命令。已处理的文档、已抽过的 chunk、已缓存的响应都会跳过，只补剩下的。

## 8. 故障排查表

### A. 索引建不起来 / 覆盖率低

| 症状 | 原因 | 处置 |
| --- | --- | --- |
| `!! cannot reach Ollama` | 服务没起 | 任务栏 Ollama 图标 → 重启，或命令行 `ollama serve` |
| `!! 'xxx' is not in ollama list` | 模型没拉 | `ollama pull qwen3:8b` |
| 覆盖率 < 50%，日志大量 `gave up on a repeating response` | 抽取模型太弱（phi3.5） | 换 `--llm qwen3:8b` |
| 覆盖率低，但日志大量 `produced no entities` 且无报错 | 分片本身太短、没实体 | 正常，属数据损耗；若想补，删 `kv_store_extracted_chunks.json` 后重跑 |
| 进程突然消失、日志无异常 | 显存不足被系统杀掉 | `--batch 4`、关掉其他占显存的程序 |
| 越来越慢 | 缓存文件被删了 | 别删 `kv_store_llm_response_cache.json` |

### B. 答案总是「文中没有提到」

| 症状 | 原因 | 处置 |
| --- | --- | --- |
| 全部题目都这样 | 上下文被 4096 token 截断 | 设 `$env:OLLAMA_NUM_CTX="8192"` 再跑 |
| 只有 Multi（跨文档）题这样 | mini 模式的图路径没召回另一半证据 | 缩小 `top_k` 让上下文更聚焦（默认 60 太宽）；或改 `--mode naive` 对照 |
| 换了模型后突然全错 | 索引与问答模型不一致 | 问答的 `--llm` 必须和建索引时一致 |
| 答案很短、像复读机 | 模型陷入循环 | 换模型；日志搜 `token repeat limit` |

### C. 程序本身报错

| 症状 | 原因 | 处置 |
| --- | --- | --- |
| `IndexError` / `维度不匹配` | 用 384 维索引配了 1024 维 embedding | 工作目录和 embedding 必须配套，别混用 |
| `ModuleNotFoundError: minirag` | 不在实验根目录 | `cd E:\miniRAG\MiniRAG` 再跑 |
| `JSONDecodeError: Unexpected UTF-8 BOM` | 某个 json 被记事本加了 BOM | 用脚本重写该文件（无 BOM） |
| 控制台中文乱码 | 代码页不对 | 用 `.bat`（内部已 `chcp 65001`），别直接敲命令 |
| `python` 无任何输出 | 见第 4 章 | 用 `.\venv_minrag\Scripts\python.exe` |

### 9.4 术语表

| 术语 | 含义 |
| --- | --- |
| chunk（分片） | 文档按 1200 token 切开的小块，是抽取和检索的基本单位 |
| 实体抽取 | 让大模型从一块文本里挑出人物/组织/地点/事件及其描述 |
| gleaning（追问） | 抽完再问模型"还有没有遗漏"，用于提高召回 |
| top_k | 一次检索返回多少个结果，越大上下文越长 |
| num_ctx | 模型的上下文窗口，Ollama 默认 4096 token |
| LLM 裁判 | 用另一个大模型按规则给答案打 1/0/-1 |

## 10. 实验报告要点（提交时写这几段）

1. **环境与方法**：本机配置、模型选择、索引参数（照抄第 6 章表）。
2. **索引质量**：覆盖率、图谱规模，以及为什么 phi3.5 不可用（复读导致抽取作废）。
3. **问答效果**：答对率 + 分题型表现（Single 通常最高，Multi 最低，Null 看是否敢说"信息不足"）。
4. **误差分析**：挑 3 条典型错例，说明是"没召回"还是"召回了但推理错"。
   - 判断方法：`rag.aquery(..., QueryParam(mode="mini", only_need_context=True))` 把上下文打出来看。
5. **改进方向**：缩小 top_k 提高上下文密度、换更大模型、或对 Multi 题做两段式检索。
